# Corex Code v0.1 specification

## Status

This document is the implementation contract for the first usable Corex Code
release. The `v0.1` branch implements this loop with Bun and Ollama. Features
explicitly listed as out of scope remain planned.

## Goal

Deliver a terminal coding agent that can understand a request, inspect a Git
repository, propose a bounded code change, ask for approval, apply the approved
change, and show the resulting diff.

## User journey

1. The user runs `corex` from a Git repository.
2. Corex loads configuration and validates the selected model provider.
3. The user describes a coding task in the interactive prompt.
4. The agent requests file reads or searches through the tool layer.
5. The agent produces a proposed patch with a short explanation.
6. Corex displays the patch and asks the user to approve or reject it.
7. Corex applies only an approved patch.
8. Corex displays `git diff` and summarizes the files changed.

## Functional requirements

### CLI session

- `corex` starts an interactive session in the current directory.
- `corex --help` documents all supported flags and environment variables.
- The terminal UI distinguishes user and assistant text, tool activity,
  warnings, errors, mode, model, provider, usage, and approval state.
- A bordered composer accepts text and submits with `Enter`.
- `Shift+Tab` cycles host-enforced Build, Plan, and Ask modes.
- `Ctrl+P` opens commands and `Ctrl+O` opens installed models.
- `Ctrl+C` cancels the current turn without corrupting repository files.
- A second `Ctrl+C`, or an explicit exit command, closes the session.

### Repository access

- Corex resolves and displays the repository root at startup.
- File paths are normalized and constrained to that root.
- Reads support text files and return a clear error for unsupported binary data.
- Search uses ripgrep when available and reports when it falls back to another
  implementation.
- Common large or sensitive paths such as `.git`, `node_modules`, and `.env`
  are excluded by default.

### Model connection

- The model adapter exposes one provider-neutral streaming interface.
- v0.1 must support at least one documented provider end to end.
- Corex opens the terminal UI immediately and checks the local model catalog in
  the background.
- `/model` opens an inline modal that can select an installed model or download
  a configured or custom model with progress and cancellation.
- `corex models list` and `corex models pull <name>` support explicit and
  non-interactive model setup.
- Credentials come from environment variables or an ignored local config file;
  they are never written to logs or prompts intentionally.
- Authentication, rate-limit, and connection failures produce actionable
  messages rather than terminating with a raw stack trace.
- JSON-text tool requests from compatible local models are accepted only when
  they name a declared Corex tool and pass normal argument validation; the raw
  JSON is not displayed as an assistant answer.

### Approval-based editing

- Model output cannot write directly to the filesystem.
- A proposed edit is represented as a structured patch.
- The user sees the affected paths and diff before approval.
- Available choices are apply, reject, or cancel the turn.
- Corex checks that a file has not changed since it was read. A stale edit is
  rejected and must be regenerated.
- Applying a multi-file patch is atomic where practical. Partial failure is
  reported precisely and must not be described as success.

### Git diff preview

- After an edit, Corex shows the repository diff for the affected files.
- Existing user changes remain distinguishable from Corex changes.
- Corex never commits, pushes, switches branches, or discards changes in v0.1.
- A non-Git directory produces a clear startup error in v0.1.

## Out of scope

The following are deliberately deferred:

- persistent SQLite memory and cross-session recall;
- autonomous command execution;
- automatic tests and linting;
- rollback and checkpoints;
- token and cost dashboards;
- dynamic multi-model routing;
- multi-agent workflows; and
- shared team sessions.

## Configuration

Configuration is loaded from `corex.config.json` in the repository root. Secrets
must remain in environment variables.

```json
{
  "provider": "ollama",
  "model": "qwen2.5-coder:7b",
  "ollama": {
    "baseUrl": "http://127.0.0.1:11434",
    "keepAlive": "5m"
  },
  "agent": {
    "maxSteps": 12,
    "maxFileBytes": 200000,
    "maxSearchResults": 100
  }
}
```

## Acceptance criteria

v0.1 is complete when an integration test can demonstrate all of the following:

1. Start Corex in a temporary Git repository.
2. Connect to a deterministic test model adapter.
3. Read and search repository files without escaping the repository root.
4. Display a proposed edit and leave files unchanged when it is rejected.
5. Apply the same edit after approval.
6. Display the resulting Git diff.
7. Redact configured secrets from logs and user-visible errors.
8. Cancel an in-progress turn without leaving a partially written file.

## Quality gates

- TypeScript compiles with strict checking.
- Unit and integration tests pass.
- Linting passes.
- Public commands and configuration fields are documented.
- No high-severity dependency vulnerability is knowingly shipped.
